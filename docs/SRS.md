## 1. 引言

### 1.1 目的

本文档定义 **DSH Manager** 的完整软件需求。DSH Manager 是一个 Windows 桌面 GUI 程序，用于管理 DeepSeek Harness（`dsh`）CLI 的安装版本与 Web 服务的运行。

本文档是实现、验收与后续变更的唯一依据。凡未在本文档中列出的特性，均视为**范围外**，不得在实现中自行添加。

### 1.2 问题陈述

当前管理 `dsh` 存在三个具体痛点：

| 痛点              | 现状                                                               |
| ----------------- | ------------------------------------------------------------------ |
| **P1** 版本不透明 | 需手动执行 `dsh --version` 与 `npm view` 对比才能知道是否有更新    |
| **P2** 升降级不便 | 需手动记忆并敲完整的 `npm install -g @deepseek-ai/dsh@<version>`   |
| **P3** 黑窗口常驻 | `dsh web` 必须在前台终端运行，终端窗口必须一直保留，关闭即服务停止 |

此外，`dsh` 可能由不同包管理器（npm / pnpm / bun / yarn）全局安装，手工管理时容易装成多份并产生 PATH 冲突。

### 1.3 范围

**范围内**：`dsh` CLI 自身的全局安装管理（版本查看、安装、更新）与 `dsh web` 服务的启停托管；**web profile 第三方插件的管理**（列出 / 安装 / 更新 / 卸载，见 §3.9）；**本程序自身的更新**（检查 / 提示 / 下载 / 静默安装并自动重启，见 §3.10）；以及**单实例运行**（重复启动只把已有实例的主窗口弹回来，见 §3.11）。

**范围外**（明确不做）：

- **禁用 / 启用插件**（DSH 自带插件页具备的能力）。本轮只做安装 / 更新 / 卸载（用户决定，见 §3.9）。
- **跨包管理器迁移**：FR-11 修订后界面不再提供 PM 选择器，迁移能力从界面撤下（事务引擎仍保留跨 PM 路径，理由见 ARCHITECTURE §4.2）。
- `dsh` 的任何配置修改、凭据管理、会话管理。
- **写 profile 的任何文件**（`package.json` / `cordis.patch.yml` / `pnpm-workspace.yaml`）；插件变更一律经 `dsh plugin` 转发（CON-5 修订）。
- `dsh` 本身的功能扩展或 bug 修复。

## 2. 总体描述

### 2.1 产品愿景

一个常驻系统托盘的轻量桌面程序，把 `dsh` 的"版本管理"和"服务启停"两件事从命令行搬到 GUI，消除黑窗口常驻问题，并自动适配用户机器上实际的包管理器环境。

### 2.2 运行环境（实测事实）

以下数据均为 2026-09-20 在目标机器上的**实测结果**，是本文档诸多设计决策的直接依据。

#### 2.2.1 工具链

| 组件          | 实测值                                                    | 是否满足要求                 |
| ------------- | --------------------------------------------------------- | ---------------------------- |
| rustc / cargo | 1.98.1                                                    | ✅（Slint 1.18 要求 ≥ 1.92） |
| Node.js       | v24.16.0                                                  | ✅                           |
| npm           | 12.0.2，位于 `C:\Software\nodejs\npm`                     | ✅                           |
| pnpm          | 12.3.4，位于 `C:\Users\xueyu\AppData\Local\pnpm\bin\pnpm` | ✅                           |
| bun           | **未安装**                                                | —                            |
| yarn          | **未安装**                                                | —                            |

#### 2.2.2 包管理器全局路径

| PM   | 全局 bin 目录                           | 全局包根目录                                      |
| ---- | --------------------------------------- | ------------------------------------------------- |
| npm  | `C:\Users\xueyu\AppData\Roaming\npm`    | `C:\Users\xueyu\AppData\Roaming\npm\node_modules` |
| pnpm | `C:\Users\xueyu\AppData\Local\pnpm\bin` | `C:\Users\xueyu\AppData\Local\pnpm\global\v11`    |

**关键结论**：npm 全局前缀位于用户目录下，因此安装/卸载全局包**不需要管理员权限**。

#### 2.2.3 PATH 顺序（决定 owner 判定的核心事实）

```
C:\Software\nodejs                      ← npm 本体
C:\Users\xueyu\AppData\Local\pnpm\bin   ← pnpm 全局 bin（在 npm 之前）
C:\Users\xueyu\AppData\Roaming\npm      ← npm 全局 bin（dsh 在此）
```

**这是本项目最重要的环境事实**：pnpm 的全局 bin 目录排在 npm 之前。若 `dsh` 同时存在于两者中，**pnpm 的那份会覆盖 npm 的那份**。因此 owner 判定必须基于 PATH 解析顺序（FR-3），且事务验证不得依赖 PATH（TR-4）。

#### 2.2.4 dsh 当前安装状态

| 项                       | 值                                                                                     |
| ------------------------ | -------------------------------------------------------------------------------------- |
| 版本                     | `0.1.6-alpha.2`                                                                        |
| 所属 PM                  | **npm**                                                                                |
| `where.exe dsh` 解析结果 | `C:\Users\xueyu\AppData\Roaming\npm\dsh`、`C:\Users\xueyu\AppData\Roaming\npm\dsh.cmd` |
| npm 全局包列表           | 含 `@deepseek-ai/dsh@0.1.6-alpha.2`                                                    |
| pnpm 全局包列表          | **不含** dsh（仅有 `@pnpm/exe@11.24.0`、`pnpm@12.3.4`、`pnpm@12.0.0`）                 |

Windows 上 npm 生成的 shim 为三件套：`dsh`、`dsh.cmd`、`dsh.ps1`（npm 同理）。

#### 2.2.5 npm 发布状态

| dist-tag | 版本                         |
| -------- | ---------------------------- |
| `latest` | `0.1.5-rc.2`                 |
| `next`   | `0.1.5-rc.2`                 |
| `alpha`  | `0.1.6-alpha.2` ← 当前已安装 |

**关键结论**：npm 的 `latest` tag（`0.1.5-rc.2`）**比已安装版本更旧**。任何把"最新版本"等同于 `latest` 的实现都会导致**误降级**。这是 FR-8 存在的直接原因。

npm 上共有 **22 个已发布版本**：

```

0.1.2-alpha.4  0.1.2-alpha.5  0.1.2-rc.1  0.1.3-alpha.2  0.1.5-alpha.1
0.1.5-alpha.2  0.1.5-rc.1  0.1.5-rc.2  0.1.6-alpha.1  0.1.6-alpha.2
```

registry 地址：`https://registry.npmjs.org/`。

⚠ **本机配了系统代理**（v1.3 修正）：HKCU `Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `ProxyEnable = 1`、`ProxyServer = http://127.0.0.1:12450`（2026-09-22 实测）。本文档 v1.2 及之前在这里写"未配置 proxy"是**错的** —— 它只看了环境变量，漏掉了 Windows 系统代理这一层，并由此派生出原 §7.3 的错误结论「代理设置：未提出需求」与 Ruling 89。程序默认走它（**FR-33**）。

#### 2.2.6 GitHub 发布状态

- 仓库：`deepseek-ai/deepseek-harness`（公开）
- Release tag 命名：`dsh-v<version>`（例如 `dsh-v0.1.6-alpha.2`）
- Release 总数：**18**
- 更新说明为**中英双语混排 markdown**，正文含裸 HTML（如 `<h3 id="...">`），单条最长 13,817 字符

**tag 与 npm 版本并非 1:1，存在双向缺口**：

| 缺口类型                         | 数量 | 具体版本                                                                           |
| -------------------------------- | ---- | ---------------------------------------------------------------------------------- |
| npm 有版本但**无** release notes | 6    | `0.0.1-rc.1`、`0.0.1-rc.2`、`0.0.1-rc.5`、`0.1.0-rc.2`、`0.1.0-rc.3`、`0.1.0-rc.6` |
| 有 release 但 npm 上**无法安装** | 2    | `0.1.3-alpha.1`、`0.1.2-alpha.1`                                                   |

因此 FR-27 必须实现"无更新说明"的优雅降级，且版本列表**只能**以 npm 为准。

#### 2.2.7 网络可达性

| 目标                                   | 结果                         | 耗时   |
| -------------------------------------- | ---------------------------- | ------ |
| `registry.npmjs.org`                   | ✅ HTTP 200                  | 4.1 s  |
| `api.github.com`                       | ✅ HTTP 200                  | 1.4 s  |
| `github.com`                           | ❌ 连接超时（curl 返回 000） | 21.1 s |
| `git ls-remote https://github.com/...` | ❌ Connection reset          | —      |

**关键结论**：

1. `github.com` **不可达**，因此不得在界面中提供指向 GitHub 网页的链接（会是死链）。
2. `git ls-remote` **不可用**，不得用 git 协议枚举 tag。
3. 仅 `api.github.com` 可用，仅用于拉取更新说明。
4. npm registry 响应需 4.1 s，**所有网络访问必须在后台线程执行**（NFR-1）。

#### 2.2.8 dsh web 运行参数

`dsh web` 等价于 `dsh --profile web`，支持参数：

| 参数                            | 说明                           |
| ------------------------------- | ------------------------------ |
| `--host <host>`                 | 绑定地址                       |
| `--port <port>`                 | 监听端口，传 `0` 由系统分配    |
| `--no-open`                     | 不自动打开浏览器               |
| `--trusted-host <authority...>` | 额外信任的 authority（可重复） |

默认端口 **3080**。编写本规范时该端口正被占用（`127.0.0.1:3080` LISTENING，PID 13432），因此 FR-16 的端口冲突处理是必需功能而非边缘情况。

#### 2.2.9 dsh profile 的内部实现（本项目的禁区）

`dsh` 内部**硬编码使用 pnpm** 管理 profile 插件，证据：

- `dsh` 用法字符串固定为 `dsh plugin --profile <name> <pnpm-args...>`
- `$DSH_HOME/profiles/web/` 下存在 `pnpm-lock.yaml`、`pnpm-workspace.yaml`、`node_modules/.pnpm/`
- `dsh` 源码直接输出 pnpm 专属报错文案：`add the exact key pnpm printed above under allowBuilds in .../pnpm-workspace.yaml`

**这与 `dsh` CLI 自身由哪个 PM 安装是两个完全独立的问题。** 本项目只管理后者。

### 2.3 用户特征

单用户、本机使用、具备命令行基础但希望避免重复敲命令的开发者。不需要多用户、不需要权限分级。

### 2.4 约束

| 编号      | 约束                                                                                                                                                                                                             |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **CON-1** | 目标平台为 Windows。实现可保持跨平台可移植性，但**只在 Windows 上验证**。                                                                                                                                        |
| **CON-2** | 使用 Slint 1.18 及其**默认 feature 集**（`std, backend-default, renderer-femtovg, renderer-software, accessibility, compat-1-2, system-tray`），不裁剪。`renderer-software` 作为 OpenGL 不可用时的兜底予以保留。 |

| **CON-4** | 网络访问只允许使用 `registry.npmjs.org` 与 `api.github.com`。**禁止**使用 `github.com` 网页、git 协议。                                                                                                          |
| **CON-5** | 对 `dsh` profile 插件的**一切变更**（安装 / 更新 / 卸载）**必须**经 `dsh plugin --profile <name> …` 转发 —— 由 dsh 自己持 profile 写锁并在成功后 reconcile bundle 列表。**不得**直接调用 `pnpm`，**不得**写 profile 的任何文件。**只读** `<profile>/package.json` 与 `<profile>/node_modules/<包>/package.json`（§3.9 的列表来源）是允许的。~~原文：不得以任何方式干预 profile 的插件管理~~（v1.4 修订，理由见 §1.3 与 ARCHITECTURE §4.8） |
| **CON-6** | 所有 `dsh` / PM 命令的调用必须使用 Windows shim 全名（`dsh.cmd`、`npm.cmd`、`pnpm.cmd`、`bun.exe`、`yarn.cmd`）。**`Command::new("dsh")` 在 Windows 上无法解析**。                                               |
| **CON-7** | 子进程创建必须携带 `CREATE_NO_WINDOW`（`0x08000000`），且二进制须声明 `#![windows_subsystem = "windows"]`。两者缺一即出现黑窗口。                                                                                |
| **CON-8** | 必须履行 Slint 免版税许可的署名义务：在"关于"对话框中显示 `AboutSlint` 组件（FR-29）。                                                                                                                           |
| **CON-9** | Slint 自动从系统获取字体，中文无需嵌入字体文件。**不得**为此引入字体资源。                                                                                                                                       |

| 编号     | 假设 / 依赖                                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------ |

## 3. 功能需求

### 3.1 启动与包管理器探测

#### FR-1 包管理器扫描

程序启动时（后台线程）扫描候选 PM：`npm`、`pnpm`、`bun`、`yarn`。

- 判据：执行 `<pm> --version` 成功返回即为"已安装"。
- 仅"已安装"的 PM 才出现在 FR-3 的下拉列表中。
- 单个 PM 探测失败不得影响其他 PM 的探测结果。

#### FR-2 全局 bin 目录获取

对每个已安装的 PM，获取其全局 bin 目录：

| PM   | 命令              |
| ---- | ----------------- |
| npm  | `npm prefix -g`   |
| pnpm | `pnpm bin -g`     |
| bun  | `bun pm bin -g`   |
| yarn | `yarn global bin` |

#### FR-3 owner PM 判定

按以下顺序判定 owner PM：

1. 执行 `where.exe dsh`，获得按 PATH 顺序排列的 `dsh` 路径列表。
2. 取**第一个**路径，判断它落在哪个 PM 的全局 bin 目录内。命中者即为 owner PM。
3. 若 `where.exe dsh` 无结果（`dsh` 未加入 PATH），退化为：依次查询各 PM 的全局包列表，**第一个**列出 `@deepseek-ai/dsh` 的即为 owner PM。
4. 若仍无结果，状态为"未检测到 dsh"，UI 显示对应提示。

**设计依据**：判定结果等于"用户敲 `dsh` 时真正执行的那一个"，这是唯一有实际意义的语义。见 §2.2.3。

#### FR-4 已安装版本读取

已安装版本一律通过执行 `dsh --version` 获取。

**不得**解析各 PM 的全局列表输出格式来读取版本（AS-4）。此设计使版本读取与 PM 解耦。

#### FR-5 PM 探测结果缓存与刷新

探测结果在启动时获取一次并缓存。以下时机必须触发重新探测：

- 任何事务（§4）完成后
- 用户在界面点击刷新

### 3.2 版本信息与渠道

#### FR-6 版本列表拉取

从 `https://registry.npmjs.org/@deepseek-ai/dsh` 拉取：

- 全部已发布版本列表（当前 22 个）
- dist-tags（`latest` / `next` / `alpha`）

**必须是异步的**，不得阻塞 UI（NFR-1）。请求超时上限见 NFR-3。

**拉取时机**：**每次程序启动时查询一次**，加上用户手动点击刷新。**不做后台轮询、不做定时检查**（已确认）。

**请求头要求**：应携带 `Accept: application/vnd.npm.install-v1+json` 以获取精简 packument —— 本需求只需 `versions` 的键集合与 `dist-tags`，不需要每个版本的完整元数据。

**注意**：响应中的 `dist-tags.latest` **不是**"最新版本"（见 FR-8）。

#### FR-7 通道判定

根据当前已安装版本，判定其所属通道：

| 版本后缀   | 通道   |
| ---------- | ------ |
| `-alpha.N` | alpha  |
| `-rc.N`    | rc     |
| 无后缀     | stable |

#### FR-8 "最新版本"定义

**"最新版本"指当前所处通道内的最新版本，而非 npm 的 `latest` tag。**

- 当前已安装 `0.1.6-alpha.2` → 所属通道 alpha → alpha 通道最新版为 `0.1.6-alpha.2` → 显示"✓ 已是最新"
- **严禁**将 `latest` tag 直接作为"最新版本"展示或作为更新目标。见 §2.2.5。

#### FR-9 主界面版本展示（v1.4 修订）

主界面必须显示：

- **已安装**版本（操作卡「当前版本」）—— 它同时是"当前装的是什么"的唯一落点
- **是否已是最新**的判定结论（同行的状态徽标：`已是最新` / `可更新` / `检测中`）

**v1.4 修订说明**：原文要求"已安装版本 + 所属通道徽标"与"最新版本 + 是否已是最新的结论"四项，其中"通道徽标"已于 v1.3 去掉（通道信息在版本号自身里），**"最新版本"这一项**随左栏版本主卡的删除而不再单独显示 —— 目标版本下拉的**默认选中项就是通道内最新版**，同一个值说两遍只是多一行（用户决定，见 ARCHITECTURE §9.3 的 1.7 条）。

#### FR-10 版本列表展开

版本下拉列表默认显示当前通道的最新版；用户可展开查看**全部**版本。

- 列表按版本号**降序**排列（最新在前）
- ~~每个版本标注其通道~~（v1.3 起不标注：通道信息本就在版本号里）
- ~~当前已安装版本需有视觉标识~~（v1.4 起不标注：改为点击〔安装〕时的**重装确认**，见 FR-12b）

**v1.4 修订的理由**：那条"← 当前"小字回答的是"我选中的是不是现在装着的"。把它从**常驻提示**改成**动作前确认**，同一个问题只在一处回答 —— 两处都留会让"选中的确实是已装版本"这件事被说两遍，而用户真正需要的判断（要不要重装）发生在点击那一刻。

### 3.4 dsh web 生命周期

#### FR-16 启动 dsh web

启动 `dsh web`，要求：

- 使用 `CREATE_NO_WINDOW`，**不得出现控制台窗口**（CON-7）
- 传递 `--port <端口>`，端口默认 3080，可在界面修改
- **不传** `--no-open`，由 `dsh web` 自行打开浏览器，本项目不重复实现该功能
- 捕获子进程 stdout / stderr 并流入日志区（FR-28）

#### FR-17 启动前端口检测

启动前先对 `127.0.0.1:<端口>` 做 TCP 连接探测：

| 探测结果                         | 行为                                                                                |
| -------------------------------- | ----------------------------------------------------------------------------------- |
| 端口空闲                         | 正常启动                                                                            |
| 端口被占用，且是本程序启动的进程 | 提示"已在运行"，提供打开网页 / 停止                                                 |
| 端口被占用，且非本程序启动       | 提示"检测到外部 dsh web 正在运行"，提供三个出口：打开网页 / 停止 / 改用其他端口启动 |

#### FR-18 运行状态展示

主界面显示 `dsh web` 的运行状态与访问地址 `http://127.0.0.1:<端口>`。

#### FR-19 停止 dsh web

| 场景                         | 行为                                                                             |
| ---------------------------- | -------------------------------------------------------------------------------- |
| 由本程序启动                 | 直接终止持有的子进程句柄                                                         |
| 外部启动（端口被占但无句柄） | 通过 `netstat -ano` 定位监听 PID → **校验该进程为 `node.exe`** → `taskkill` 终止 |

**校验进程名是强制步骤**，避免误杀占用同一端口的其他程序。

#### FR-20 打开网页

提供"打开网页"按钮，在默认浏览器中打开 `http://127.0.0.1:<端口>`。实现方式为 `explorer.exe` + **单个参数**（无 shell 层，配合 `CREATE_NO_WINDOW`），并加 http(s) 协议白名单（`dsh::is_web_url`），不引入额外依赖。

> **v1.6 更正**：原文写的是 `cmd /c start "" <url>`。Ruling 65 已把它换掉 —— URL 来自**网络**（FR-27b 的 release notes 正文链接），属信任边界，而 Rust 的参数编码**不**转义 cmd 的元字符（`& | ^ < > % !`）。同一条白名单现在也是正文链接的准入判据，见 FR-27b。

#### FR-21 退出语义

从托盘菜单"退出"时：**必须先停止由本程序启动的 `dsh web`，再退出进程**，不得遗留孤儿 `node.exe` 进程。

若用户希望保留 `dsh web` 运行，应使用"隐藏窗口"而非"退出"。

#### FR-22 崩溃后的孤儿进程

本程序异常终止时，`dsh web` 子进程可能成为孤儿进程继续运行。重新启动本程序时，**FR-31 持久化的运行态端口**会告诉程序该探测哪个端口，从而将其识别为"外部 dsh web"，用户可通过 FR-19 停止。

**本机制依赖 FR-31**：若运行态端口未被持久化（或持久化失败），程序将只探测偏好端口，非默认端口上的孤儿会**静默失联** —— 界面显示"已停止"，而实际上有一个 `dsh web` 在后台运行。实测该进程占用约 **289 MB** 内存（§2.2.8）。因此 FR-31 不是可选优化，而是本恢复机制的前提。

### 3.5 托盘常驻

#### FR-23 窗口隐藏与托盘

- 关闭主窗口时**不退出程序**，改为隐藏窗口
- 程序始终保持托盘图标常驻
- 必须使用 `run_event_loop_until_quit()`，**不得**使用 `run_event_loop()`（后者在窗口隐藏时会退出事件循环，导致托盘一同消失）

**实现机制的实测澄清**（依据见 [ARCHITECTURE.md](ARCHITECTURE.md) §2.4.2）：

1. `close-requested` **作为 Slint 语言回调并不存在**（[slint-ui/slint#6401](https://github.com/slint-ui/slint/issues/6401) 仍为 open）。拦截能力只存在于语言绑定侧，API 为 `slint::Window::on_close_requested(impl FnMut() -> CloseRequestResponse + 'static)` —— **挂在 `slint::Window` 上，不在生成的组件上**。
2. **Slint 的默认关闭行为就是隐藏窗口**。因此本需求**不需要任何自定义代码即可满足**：`run_event_loop_until_quit()` + 在 `main` 中持有组件句柄即可。
3. 若注册该回调，**必须返回 `CloseRequestResponse::HideWindow`**。返回 `KeepWindowShown` 会**取消**关闭，表现为**点 X 按钮毫无反应，且不产生任何报错**。
4. 注册回调的正当用途仅为附带副作用：写日志、首次关闭时提示"程序仍在托盘运行"。

#### FR-24 托盘菜单

托盘菜单按状态动态构建（Slint 会在绑定的属性变化时自动重建平台菜单）：

```
显示主窗口
打开 DSH 网页        ← 仅 dsh web 运行中可用
────────────────
启动 dsh web         ← 仅 dsh web 已停止可用
停止 dsh web         ← 仅 dsh web 运行中可用
────────────────
退出
```

平台行为约束（Slint 在 Windows 上的既定行为，不可更改）：

- **左键单击**托盘图标触发 `clicked()` 回调
- **右键单击**弹出菜单

#### FR-25 托盘组件与主窗口的状态同步

由于 Slint 的 `SystemTrayIcon` 实例与 `Window` 实例**不共享 global 变量**（各自持有独立副本），要求：

- **Rust 侧持有唯一的状态源**（`AppState`）
- 每次状态变化时，**同时推送**到主窗口实例与托盘实例

**不得**尝试通过 Slint global 在两个实例间共享状态。这是硬约束，违反必然导致状态不一致。

#### FR-27 更新说明渲染与降级

| 情况                                   | 行为                                                      |
| -------------------------------------- | --------------------------------------------------------- |
| 请求成功                               | 使用 `slint::StyledText::from_markdown` 渲染 release body |
| 该版本无 release（§2.2.6 的 6 个版本） | 显示"该版本无更新说明"                                    |
| 网络失败 / 超时                        | 显示失败提示，**不得**影响界面其他功能                    |

markdown 渲染使用 Slint 内建能力，**不得引入额外 markdown 解析库**。

**必须做轻量预处理（阻塞性要求）**

Slint 的 `StyledText` 官方 **Currently Unsupported** 列表包含 **Headings（标题）** 与 **Other HTML tags（其他 HTML 标签）**。而 §2.2.6 已查明 DSH 的 release notes 正文：

- 通篇使用 `### 新增功能`、`### 体验优化` 这类 ATX 标题
- 混有裸 HTML，如 `<h3 id="cn-v0.1.6-alpha.2">新增功能</h3>`

若不预处理，这些内容会**原样显示成 `### 新增功能` 和 `<h3 id="...">` 这样的垃圾文本**。因此渲染前必须做最小转换：

1. 剥离裸 HTML 标签，**保留标签内的文本**
2. ATX 标题降级为粗体（`### 新增功能` → `**新增功能**`）
3. 其余语法（粗体 / 斜体 / 行内代码 / 链接 / 列表）由 `StyledText` 原生支持，**不做干预**

**明确不做**：不做完整 markdown 解析、不做目录生成。

**语言显示：不做中英切换**

release notes 正文为中英双语混排（§2.2.6）。**决定：显示全文，不提供语言切换。** 切分双语需要解析 `#cn-` / `#en-` 锚点结构，属增量功能，已确认不做。

#### FR-27b 更新说明中的链接

说明正文自带的**绝对 http(s)** 链接（如正文末尾的 Full Changelog）通过 `StyledText` 的 `link-clicked(link)` 回调交给系统默认浏览器打开；**非 http(s) 的**（站内锚点 / 相对路径 —— 就是开头那条 `[中文](#cn-...) | [English](#en-...)` 导航行）**不派发**，见下。

**适用范围澄清**：§5.2 中"禁止指向 GitHub 网页的界面链接"指的是**本程序不得主动生成** GitHub 网页链接（因 §2.2.7 实测 `github.com` 不可达，生成的会是死链）。release notes **正文中自带的 http(s)** 链接不属于此列 —— 它们是 DSH 自身的内容，本程序只做透传，不为其可达性负责。

**非 http(s) 的正文链接不打开、也不报错**（v1.6 补充）：正文里除了真链接，还有两类**站内**目标 —— 开头的语言导航行（实测 20 个 dsh release 的正文第一行全是它，锚点链接共 40 条；写法不止一种：`#cn-v0.1.7-alpha.2`/`#en-v0.1.7-alpha.2`，更早的 release 用 `#chinese`/`#english` 与 `#cn`/`#en`），以及 `[SAFETY.md](SAFETY.md)` / `[BRAND_GUIDELINES.md](BRAND_GUIDELINES.md)` 这类**相对路径**（共 6 条）。面板里没有锚点目标（见上「语言显示：不做中英切换」），它们既打不开，也不是"打开失败"。

因此**准入与 `open_url` 的白名单共用同一个判据 `dsh::is_web_url`**：只有绝对 http(s) 地址才派发打开（`main::dispatch_notes_link` 是唯一的准入点），其余**不派发、不打开、不报错**。白名单本身（Ruling 65）不变 —— 它仍是 `open_url` 里的那道，非 http(s) 在 `spawn` 之前就 `Err`。

原实现不加判别就派发，于是用户每点一次语言导航行，日志里就多一条 `打开网页失败: 拒绝打开非 http(s) 链接: #en-v0.1.7-alpha.2`（用户报的刷屏）。

#### FR-28 日志面板

3. **复制的是屏幕所见的正文**（`$ `/`✓ `/`ER:`/`WR:` 前缀已剥掉），插入光标不显示、打字不改内容；无障碍角色显式保持 `text`（`TextInput` 的默认角色是 `text-input`，不写它读屏会把每行日志当成可编辑输入框）。

### 3.8 配置持久化

程序必须在本机持久化用户偏好（端口、关闭行为、主题、出网代理）。全部偏好**存放在同一个文件中**，因为文件路径解析、读取、损坏回退与写入这四项基础设施是共用的。

**存储位置**：`%APPDATA%\dsh-manager\state.json`

- 路径通过 `std::env::var_os("APPDATA")` 获取，**不得引入 `dirs` 等额外依赖**（见 ARCHITECTURE §7.2）
- 若 `APPDATA` 不可用（罕见），则降级为"不持久化"并记录日志，**不得阻止程序启动**

**文件结构**（实际落盘形状；字段为 `null` 或缺失一律按"**没记过**"处理，缺省值见各 FR）：

```json
{
  "preferred_port": 3080,
  "running_port": 8080,
  "close_behavior": "hide",
  "theme_mode": "auto",
  "use_system_proxy": true
}
```

> ⚠ **v1.3 修正**：本块原写作"两个字段，缺一不可"，且把运行态端口画成一个**子对象**（`{"running": {"port": 8080}}`）。实现落盘的一直是**扁平**的 `running_port`；v1.2 之后又陆续加入了 `close_behavior` 与 `theme_mode`（主题子系统），本次加入 `use_system_proxy`（FR-33）。本块现改为与实现逐字一致 —— 它此前与代码不符，而 §8.2 的验证清单是照着代码写的，所以没有任何测试或验证会发现这段文档在说谎。

#### FR-30 偏好端口持久化

持久化用户选择的端口，使其在程序重启后仍然有效。

| 项       | 要求                                                       |
| -------- | ---------------------------------------------------------- |
| 写入时机 | 用户修改端口字段时                                             |
| 读取时机 | 程序启动时                                                     |
| 缺省值   | 文件不存在、字段缺失或文件损坏时使用 **3080**（dsh 的内置默认值） |

#### FR-31 运行态端口持久化

持久化"**由本程序启动的** `dsh web` 当前监听的端口"，用于在异常终止后定位孤儿进程（FR-22）。

| 项       | 要求                                                                                                 |
| -------- | ---------------------------------------------------------------------------------------------------- |
| 写入时机 | `dsh web` 启动成功**且端口就绪确认之后**                                                              |
| 清除时机 | `dsh web` 停止之后。**包括全部停止路径**：用户手动停止、事务中的临时停止（§4）、以及 FR-21 的退出停止 |
| 读取时机 | 程序启动时                                                                                              |
| 权威性   | 该字段**仅作提示**。程序读取后探测对应端口；**若端口空闲则视为过期并清除该字段**                        |

**唯一写入点约束（强制）**：该字段的写入与清除**只允许发生在一处** —— `dsh web` 的启动/停止路径内部。任何其他代码路径都不得修改它。

**依据**：该字段一旦与实际运行状态脱节，就会重新产生它本要解决的问题 —— 孤儿失联。把写入点收敛到唯一位置，是让"脱节"在结构上不可能发生，而不是靠每处调用点自觉。

#### FR-32 持久化失败的处理

| 情况                  | 行为                                                                       |
| --------------------- | -------------------------------------------------------------------------- |
| 文件或字段不存在      | 使用缺省值，**静默**处理                                                   |
| 文件损坏 / JSON 非法  | 使用缺省值 + 记录日志；**不得阻止程序启动**，**不得弹出错误对话框**         |
| 父目录不存在          | 自动创建                                                                   |
| 写入失败              | 记录日志；**不得使用户正在进行的操作失败**                                 |

**依据**：持久化提供的是便利性（FR-30）与孤儿可发现性（FR-31）。它属于**尽力而为**的能力 —— 失败时程序的其余功能必须完全不受影响。尤其是写入失败绝不能让"启动 `dsh web`"这个主操作失败。

**关于 `running` 字段的过期判定**：程序启动时读取 `running.port` 并对其做 TCP 探测（FR-17 的同一机制）。若端口空闲，说明上次的实例已正常退出而字段未被清除（例如写入失败），此时**清除该字段并继续**，不报错。

#### FR-33 出网代理

程序自身的两个出网请求（registry 版本目录、GitHub 更新说明）**必须能走 Windows 系统代理**，且用户可关闭这一行为。

| 项       | 要求                                                                                                            |
| -------- | --------------------------------------------------------------------------------------------------------------- |
| 取值来源 | HKCU `Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `ProxyEnable`（须**恰好为 1**）与 `ProxyServer` |
| 地址形状 | `host:port`（单地址管所有协议）与 `http=…;https=…`（按协议分列）**两种都要认**；分列时 **https 优先、http 兜底**     |
| 开关     | 设置面板一档「网络代理」：**使用系统代理（缺省）** / 直连                                                          |
| 优先级   | **环境变量（`HTTPS_PROXY` 等）> 系统代理 > 直连**                                                                  |
| 作用范围 | **仅本程序自身**。`dsh web` 是独立进程，它跟的是它自己的环境变量，本程序**不得**替它决定（§1.3 范围）              |
| 缺省值   | `state.json` 没记过（`null` 或字段缺失）时按**使用系统代理**；文件缺失 / 损坏同样按使用系统代理                       |
| 失败处理 | 读注册表或解析地址的任何一步失败 → **退化为直连**；绝不 panic、绝不让出网路径整体失败（FR-32 的同款精神）            |

**依据**：`ureq` 的默认 feature 集**不做系统代理发现**，只读环境变量。原 §7.3 把"代理设置"列为"不做"，理由写的是"当前环境未配置代理" —— 该前提经实测**不成立**（§2.2.5）：本机直连 `api.github.com` 得 HTTP 403（出口 IP 的小时配额），而经系统代理 `127.0.0.1:12450` 返回 200，于是**只有本程序**上不了网，而用户完全无从判断原因（Ruling 89）。读取系统代理**不需要新增依赖**：走的是 `windows-sys` **已启用**的 `Win32_System_Registry` feature，与 `src/theme.rs` 的注册表变更监视同一套 API（ARCHITECTURE §7.2 的依赖约束因此不受影响）。

**环境变量优先是刻意的**：它在 FR-33 之前就是唯一生效的方式，且 **V-6 正是靠注入 `HTTPS_PROXY` 才验成的**。把环境变量排在最前，使本需求在语义上是**纯加法** —— 只可能多给一个候选，不会从任何已在用环境变量的人手里拿走那条路。

**缺省选「使用系统代理」的理由**：装了没配代理的机器上 `ProxyEnable` 是 0，这一档自动退化成直连，**代价是零**；反过来（缺省直连）等于把上面那个"只有本程序出不去网"的坑，原样留给每一个没改过设置的用户。

**未做**：`ProxyOverride`（绕过列表）。上限是"该直连的走了代理" —— 是安全的**那一侧**，不是"该走代理的直连了"。升级路径是 `ureq` 的 `ProxyBuilder::no_proxy()`。同族的第二个缺口一并记在这里：系统代理那条路上 `NO_PROXY` 不生效（`Proxy::new` 不带 no_proxy），只有当"没设任何 `*_PROXY`、只设了 `NO_PROXY`、又配了系统代理"时才撞得上。

### 3.9 插件管理（v1.4 新增）

管理 **web profile**（`%DSH_HOME%\profiles\web`，`DSH_HOME` 缺省 `%USERPROFILE%\.dsh`）里已装的**第三方插件**。设计依据、11 条已核实事实与取舍见 `docs/superpowers/specs/2026-09-22-plugin-manager-design.md`。

#### FR-34 插件列表

主界面右栏（更新说明之上）显示一张插件卡，列出 profile `package.json` 的 `dependencies` 里的每个包：

| 列 | 来源 |
| --- | --- |
| 名称 | `dependencies` 的键 |
| 规格 | `dependencies` 的值（原样，`^1.1.0` 与 `1.2.1` 混排是现状） |
| 已装版本 | `<profile>/node_modules/<包>/package.json` 的 `version`；读不到 → "未安装" |
| 最新版本 | `https://registry.npmjs.org/<包>` 的 `dist-tags.latest`；查不到 → "—" |

- **列表来源只允许是 `dependencies`**：`node_modules` 里有不在依赖里的传递依赖，列进来就与 `dsh plugin --profile web list` 对不上。**不得**加包名过滤（profile 的 `dependencies` 本来就只有第三方插件）。
- **可更新 = 最新版严格大于已装版本**。两者有一个未知、或最新版更旧（包被回滚过）都不算 —— 后者若判成可更新，点下去就是把用户**降级**。
- 卡头显示汇总（"6 个 · 1 个可更新"），卡底显示状态（加载中 / 读取失败 / 空）。
- 触发时机：**程序启动、用户点刷新、每次插件操作完成后**。不做后台轮询。

#### FR-35 安装插件

插件卡提供输入框 + 〔安装〕：

- 输入规格必须是 **registry 包规格**（`名称` 或 `名称@版本`）。**字符集白名单**：名称段 `[A-Za-z0-9._~-]`（`pkg` 或 `@scope/pkg`），版本段 `[A-Za-z0-9.+-]`。
- **必须拒绝**：`file:` / `link:` / `git+` / `github:` / `http(s):` / 绝对与相对路径 / 空白 / 引号 / `^1.0.0` 这类范围。两条理由：① 它们会让 pnpm 去本机路径或远端 git 取代码并执行其构建脚本；② CON-4 只允许两个**主机**。
- 校验不通过时只给状态栏提示，**不发命令、不写日志**。
- 命令：`dsh plugin --profile web add <规格>`。

#### FR-36 更新插件

| 动作 | 命令 |
| --- | --- |
| 单行〔更新〕 | `dsh plugin --profile web add <包>@<查到的 latest>` |
| 〔全部更新〕 | `dsh plugin --profile web add <包1>@<v1> <包2>@<v2> …`（**一次子进程**） |

- **更新用 `add <包>@<版本>` 而不是 `pnpm update`**：前者目标确定，不依赖 pnpm 的 range / save-prefix 语义。现状里有精确钉死的版本，`pnpm update` 对它们不会动，用户会看到"点了没反应"。
- **〔全部更新〕的取舍**：一条命令、一荣俱荣 —— 任一规格失败则整批不生效（日志里有 pnpm 原文，可退回逐行更新）。换来的是**一次**加锁 + **一次**解析安装。
- **〔更新〕只在真有更新或未安装时出现**：已是最新的行不显示它（禁用不如不显示）。

#### FR-37 卸载插件

- 行内〔卸载〕**只弹确认框**，不派发；确认框里的〔卸载〕才派发 —— 这是本功能唯一的破坏性动作。
- 确认框必须显示包名与已装版本；Esc / 点遮罩 / 右上角关闭 = 取消。
- ⚠ 确认时**必须按行下标从当前列表取回那一行**（而不是用弹框时记下的包名）：列表可能在这期间被刷新过，用户确认的是他当时看到的那一行。
- 命令：`dsh plugin --profile web remove <包>`。

#### FR-37b 插件操作的通用约束

- **不停 `dsh web`**：`dsh plugin` 与运行中的服务**共用同一把 profile 写锁**（spec F9），停服务会杀掉用户正在跑的会话。这一条推翻了设计初稿的"必须先停 dsh web"，理由见 ARCHITECTURE §9.3 的 1.7 条。
- **成败都重新盘点**：失败时用户更要看到"列表其实没变"。
- 所有命令的原文与子进程输出**必须进日志面板**（FR-28）。pnpm 因 `allowBuilds` / `minimumReleaseAge` 拦下时，本项目**不代改** `pnpm-workspace.yaml`，只把原文交到用户手里。
- 操作期间复用 FR-15 的 `busy` 闸门：与版本事务互斥。

### 3.10 本程序自身的更新（v1.5 新增）

**依据**：v0.2.1 起本仓库有了 GitHub Release（发布物由 CI 产出，见仓库根的
`.github/workflows/release.yml`）。在它之前，"怎么知道自己该升级了"这件事只能靠用户自己去
Release 页看 —— 而本程序管理的 `dsh` 反倒有完整的版本检查（FR-6）。这一节把同一件事补给
本程序自己。

#### FR-38 检查本程序自身的更新

| 项       | 要求 |
| -------- | ---- |
| 端点     | `https://api.github.com/repos/hilariouhiss/DSH-Manager/releases/latest`（**api.github.com**，CON-4 允许的主机） |
| 时机     | **每次启动查询一次** + 帮助菜单〔检查更新〕。**不做后台轮询、不做定时检查**（与 FR-6 的 Q-3 同一条已确认结论） |
| 判据     | 远端 tag 去掉前缀 `v` 后**严格大于** `CARGO_PKG_VERSION` 才算"有新版本"。相等不算；远端更旧（被回滚过）不算 —— 否则点下去就是给用户**降级**（与 FR-34 的"可更新"同一判据） |
| 排除     | `prerelease` / `draft` 一律不算（`releases/latest` 本就不返回它们，这里再挡一道，免得换端点后把测试版推给所有人） |
| 资产定位 | 安装包资产名固定为 `dsh-manager-v<版本>-windows-x64-setup.exe`，与 `installer/dsh-manager.iss` 的 `OutputBaseFilename` **逐字一致**。名字对不上时**必须报错**（说明该 release 漏传安装包），**不得**报成"已是最新" —— 否则发布流程坏了也没人知道 |
| 提示形式 | ① 顶栏右侧常驻徽标「有新版本 v<版本>」，点它开详情框；② **启动时自动弹一次**模态框（〔以后再说〕/〔忽略此版本〕/〔下载并安装〕） |
| 忽略记忆 | 记进 `state.json` 的 `skipped_app_version`（字符串）。被忽略的版本**不再自动弹框**，但徽标一直在 —— 用户忽略的是"每次开机被问一遍"，不是"不许知道有新版本" |
| 提示与忽略的解耦 | 自动弹框只发生**每会话一次**；手动〔检查更新〕**每次都弹**（用户明确要求看），且忽略过也照弹 |
| 失败处理 | **启动时的失败只进日志**（用户没要求程序去查，开机甩一句"检查更新失败"是噪音）；手动检查的失败进状态栏。`Err`（没查出结论）与"已是最新"**必须分开** —— 把网络故障显示成"已是最新"是替用户下结论 |
| 出网     | 复用 FR-33 的代理解析（环境变量 > 系统代理 > 直连）；超时沿用 NFR-3 的 15 s |

#### FR-39 下载并引导安装

| 项       | 要求 |
| -------- | ---- |
| 地址来源 | 安装包与 `SHA256SUMS.txt` 都取 release JSON 里 `assets[].url`（**api.github.com**）。**不得**用 `browser_download_url` —— 那是 `github.com`，本机实测不可达，也正是 GC-4 禁止本程序构造的那类链接。程序亦**不生成**任何 `github.com` 网页链接 |
| 信任边界 | 下载前校验资产地址前缀必须是 `https://api.github.com/repos/`（URL 来自响应体，不是本程序拼的） |
| 超时     | 安装包单独给 **120 s**。NFR-3 的 15 s 是给元数据请求的：安装包已 8.7 MB，按 15 s 算等于要求 4.6 Mbps，慢线路必然失败 |
| 体积上限 | 显式设 **64 MB**。ureq 的默认上限是 10 MB，而安装包已 8.7 MB —— 再长几版就会撞上，且报的是 `body too large` 这种与"下载失败"毫无相似之处的错 |
| 校验     | 有 `SHA256SUMS.txt` 且其中确有本资产的条目时**必须比对**：不匹配 → **删除已下载的文件并报错，不得启动安装程序**。没有该资产、或算不出哈希（`certutil.exe` 不可用）→ 记日志后**继续**。它防的是"下了一半/内容损坏"，不是防 GitHub 被攻破 |
| 哈希实现 | 用系统自带的 `certutil.exe -hashfile … SHA256`，**不新增依赖**（GC-2 的精神）。解析按**形状**取那行 64 位十六进制，**不按文案** —— certutil 的首末行随系统语言变化 |
| 落盘     | `%TEMP%dsh-manager-update<资产名>`（本程序自己的子目录：安装程序要在本程序退出后继续读它；装完由下一次启动清空，见下表） |
| 安装     | 启动安装程序（**静默、不等待** —— 安装程序要活到本程序退出之后，而它替换的正是本程序的 exe），然后本程序退出。参数固定为 `/SILENT /NORESTART`（v1.8 修订） |
| 静默的边界 | **`/SILENT` 而不是 `/VERYSILENT`**：保留一个安装进度窗，用户看得见"正在装"，全程**不需要点击**。**刻意不传 `/SUPPRESSMSGBOXES`** —— 真出事时（当初装在受保护目录、这次没有写权限…）错误框照常弹出；静默失败比多点一下糟得多。`/NORESTART` 挡掉静默模式下 Inno 的 "Reboot now?" 询问框（Inno 帮助原文："If a restart is necessary and the /NORESTART command isn't used and Setup is silent, it will display a Reboot now? message box"） |
| 装进已有目录 | **不传 `/DIR`**，靠 Inno 的 `UsePreviousAppDir`（缺省值 `yes`，已核对帮助原文）：升级时 Setup 自己从注册表取回上一次的安装目录。传 `/DIR` 反而不对 —— 本程序只知道自己 exe 在哪，开发机上那正好是 `target\release`，等于把一次更新变成新装一个目录 |
| 装完自动重启 | 安装包 `[Run]` 里有一条 `Flags: nowait skipifnotsilent runasoriginaluser` 的条目，**静默安装结束时自动把本程序拉起来**（v1.8 修订）。用户点过〔下载并安装〕之后一下都不用再点 |
| 为什么重启只能由安装程序做 | 本程序必须**先退出**才能换掉自己的 exe，所以"装完把它拉起来"只有还活着的安装程序做得到。`skipifnotsilent` 是文档明写的判据（"Instructs Setup to skip this entry if Setup is not running (very) silent"）；**不能**靠"把原有那条的 `skipifsilent` 去掉"实现 —— `postinstall` 的语义是"在完成页上放一个勾选框"，而静默模式没有完成页，它在静默下到底跑不跑文档没写死 |
| 退出语义 | **这是 FR-21 的例外**：退出时**不得**停止本程序启动的 `dsh web` —— 用户可能正在浏览器里用那个会话。`running_port` 在启动 `dsh web` 时已落盘（FR-31），所以重启后的程序会按 FR-22 把它认成"外部 dsh web"，界面显示运行中、可继续使用或自行停止。**托盘/菜单"退出"仍按 FR-21 先停**，两条路径共用同一段实现、只差一个开关 |
| 退出的幂等 | 退出路径只走一次，**先到的那条说了算**（v1.8 修订）。理由与时序有关：静默安装时安装程序会用 Restart Manager **关停占用文件的程序**（`CloseApplications=yes`），那会给本程序发一次 `WM_CLOSE`；若无条件按「关闭行为 = 彻底退出」执行，它会把上一行那条"不停 `dsh web`"的承诺当场推翻（用户正在用的会话被 `taskkill`） |
| 安装包的清理 | 装完后安装包**不留着**（v1.8 补，用户要求"安装完成后删除安装包"）：由**下一次启动**删掉整个 `%TEMP%\dsh-manager-update\`。**为什么不是"装完立刻删"**：本程序在安装期间是死的（必须先退出才能换掉自己的 exe），而安装程序也删不掉它 —— 那个文件正被 SetupLdr 占着（它要等内层 setup 跑完）。更新成功后本程序几秒内就会被安装程序拉起来，用户感知上仍然是"装完就没了"；顺带还清掉"下载了却没能启动安装程序"（例如 spawn 失败）留下的残包。只删这个专属目录、**不碰** `%TEMP%` 里别的东西；删不掉也不算错误（下次启动再试）—— 删成功与删失败都在日志面板里说一句 |

**范围内但刻意不做**：下载进度百分比（状态栏一句话 + 日志足够，且要进度就得把 worker 的
字节流搬过消息通道）。

**v1.8 修订（更正一条错误理由）**：原先把"安装完成后自动重启本程序"列在上面这段"刻意不做"里，
理由写成"Inno 的 `RestartApplications` 缺省就会做"。**那个理由不成立**：`RestartApplications`
只重启"被 Setup 用 Restart Manager **关掉**的"程序，而本程序是**自己退出**的，且没有调
`RegisterApplicationRestart`（Inno 帮助原文："For Setup to be able to restart an application
after the installation has completed, the application needs to be using the Windows
RegisterApplicationRestart API"）。所以 v0.4.0 的实际行为是：向导走完，程序**不会**自己回来 ——
这正是本轮要修的两件事之一。

**用户可见的时序**（真机实测，见 [VERIFICATION.md](VERIFICATION.md) §10）：点〔下载并安装〕→ 日志两条
→ 安装进度窗出现（此时本程序已退出）→ 约 1.5 s 后进度窗消失、本程序自动回来，**全程零点击**。

### 3.11 单实例运行（v1.8 新增）

**依据**：v0.4.0 的行为是"再双击一次图标就再起一个实例"—— 两个实例各写各的 `state.json`
（后写覆盖先写，见 ARCHITECTURE §4.4.6）、两个托盘图标、两个窗口，用户没法判断哪个才是"那个"。
用户要求：**再次尝试启动应用时，直接弹出已有进程的主窗口，而不是再启动一个实例。**

#### FR-40 单实例

| 项       | 要求 |
| -------- | ---- |
| 判据     | 进程启动时创建一个**具名互斥体**；`CreateMutexW` 报告"已存在"即为第二个实例。名字带 `Local\` 前缀 —— 按**登录会话**隔离：同一台机器上另一个用户（快速用户切换）不该被挡住，两个会话各有各的 `state.json` 与自己的 `dsh web`，没有可争用的东西 |
| 第二个实例的行为 | **立刻退出**：不建窗口、不建托盘、不写 `state.json`、不探测包管理器。退出前把已有实例的主窗口**弹回来** |
| 弹回来的语义 | 三种状态都必须能被拉回来：**已隐藏到托盘**（点 X 的缺省行为）、**已最小化**、**被别的窗口盖住**。窗口要重新可见、还原、并成为前台窗口 |
| 谁来显示窗口 | 由**第一个实例自己**调 Slint 的 `show()`，第二个实例只发一个"请弹窗"的信号。⚠ 不能让第二个进程从外部 `ShowWindow`：Slint 1.18 的 winit 后端在可见性状态没变时直接早退，外部改过之后它仍以为窗口是隐藏的，此后本进程的隐藏/关闭全部变成空操作（窗口关不掉） |
| 前台 | 显示之外还要 `SetForegroundWindow`（`w.show()` 只保证"显示"，最小化的窗口仍是最小化、被盖住的也不会自己跑到前面）。⚠ 前台锁按**调用进程**判，所以要由**第二个实例**（它是用户这次点击拉起来的、持有这份权利）先 `AllowSetForegroundWindow(ASFW_ANY)` 再发信号 |
| 不误判 | `CreateMutexW` 失败（句柄为 NULL）时**不认领**，退化成"允许第二个实例"。误判成"已有实例"的代价是**谁也起不来**，比多开一个窗口糟得多 |
| 与更新的配合 | 静默安装结束后由安装程序把本程序拉起来，此时旧实例早已退出、互斥体已释放 —— 单实例不会把"更新后的重启"挡在门外 |

## 4. 事务模型与原子性

### 4.1 原子性契约

npm / pnpm / bun / yarn **均不提供事务能力**，因此严格意义的原子性无法实现。本程序提供的是 **saga 补偿契约**：

> **要么操作成功，要么回到操作前的状态。若连补偿都失败，必须明确报告降级状态并给出可直接复制执行的手动恢复命令。绝不允许静默地停留在半成品状态。**

### 4.2 事务定义

```
事务 T:  (PM_old, V0)  ──►  (PM_new, V)
```

#### 4.2.1 前置检查（任何一条不通过即拒绝，零副作用）

| 编号     | 检查项                                   | 不通过时的处理                                    |
| -------- | ---------------------------------------- | ------------------------------------------------- |
| **TR-1** | `dsh web` 已停止                         | 先停止，或由用户确认后停止（避开 Windows 文件锁） |
| **TR-2** | `PM_new` 可用（`--version` 执行成功）    | 拒绝执行                                          |
| **TR-3** | **`PM_new` 的全局 bin 目录位于 PATH 中** | **拒绝执行**                                      |

**TR-3 的依据**：若目标 PM 的 bin 目录不在 PATH 中，事务完成后 `dsh` 将从 PATH 上消失。这是**动手前即可发现**的问题，因此必须阻断，而不是事后告警。

#### 4.2.2 步骤

| 步骤   | 动作                                                |
| ------ | --------------------------------------------------- |
| **S1** | `install(PM_new, V)`                                |
| **S2** | `verify(PM_new, V)` —— **不得经由 PATH**（见 TR-4） |
| **S3** | 若 `PM_old ≠ PM_new`：`uninstall(PM_old)`；否则跳过 |
| **S4** | `verify_final()` —— 经 PATH 解析并实际执行          |

#### 4.2.3 补偿流程

任一步骤失败即进入补偿：

```
C1  探测 PM_old 上的 V0 是否仍然完好（直接执行其 dsh.cmd --version，不走 PATH）
C2  ├── 完好   → 卸掉 PM_new 上的残留，使状态回到 (PM_old, V0)
    └── 已损坏 → 重新 install(PM_old, V0)，然后卸掉 PM_new 上的残留
C3  ├── 补偿成功 → 报告"操作失败，已恢复到 <PM_old> <V0>"
    └── 补偿失败 → 报告降级状态 + 输出两条可复制的手动命令
```

### 4.3 强制技术要求

#### TR-4 验证不得经由 PATH

**S2 必须直接执行 `<PM_new 全局 bin 目录>\dsh.cmd --version`，不得依赖 PATH 解析。**

**依据**：实测 PATH 中 `pnpm\bin` 位于 `npm` 之前（§2.2.3）。在执行 `pnpm → npm` 迁移时，装完 npm 那份后 `where dsh` **仍指向 pnpm 的旧文件**，此时执行 `dsh --version` 验证的是旧的那份，会**假通过**。

#### TR-5 补偿前必须先探测 PM_old 的完好性

**不得盲目执行"卸载 PM_new"作为回滚。**

**依据**：若 S3 的 `uninstall(PM_old)` 失败并已将 PM_old 破坏，此时再卸载 PM_new 将导致**两边都不可用**。正确逻辑是先确认 PM_old 可执行，仅在其完好时才卸载 PM_new；若其已损坏，应反向重装 PM_old。

#### TR-6 迁移顺序不可颠倒

**必须先安装新的，再卸载旧的。严禁先卸载再安装。**

| 顺序        | 中途失败的最坏结果                                                           |
| ----------- | ---------------------------------------------------------------------------- |
| ❌ 先卸后装 | **机器上一份 `dsh` 都没有**，且无法用本程序修复（程序自身依赖 `dsh` 可用性） |
| ✅ 先装后卸 | 安装失败 → 原状不变；卸载失败 → 两份共存，功能正常，仅略有冗余               |

最坏情况由"完全不可用"降级为"存在冗余"，这是本顺序的根本价值。

#### TR-7 事务完成后的重新探测

事务结束（无论成功或失败）后必须：

1. 重新执行 FR-1 ~ FR-4 的探测（owner PM 可能已改变）
2. 将新状态推送到主窗口与托盘两个实例（FR-25）
3. 若事务前 `dsh web` 处于运行状态，重新启动它

#### TR-11 补偿中的所有动作必须先探测目标状态再执行

**TR-5 的推广**：不仅 `PM_old` 需要先探测，补偿流程中的**每一个**动作都必须先确认其目标状态是否存在，再决定是否执行。

**依据**：补偿流程中会执行"卸载 `PM_new` 的残留"。若 `PM_new` 上根本不存在 `dsh`（这在 S1 失败时会自然发生），卸载命令会以非零码退出，从而被**误判为补偿失败**，最终错误地报告 `Degraded` —— 让用户以为环境已损坏，而实际上一切正常。

因此补偿的正确形态是：

```
C2  清理 PM_new 残留：
    ├── 探测 PM_new 上是否存在 dsh
    │   └── 不存在 → 跳过卸载（本就干净，视为成功）
    └── 存在 → 执行卸载，失败才计为补偿失败
```

**这条规则是"幂等探测"原则的体现**：补偿动作只描述*目标状态*（"PM_new 上不应有 dsh"），而不是*动作序列*（"执行卸载命令"）。

### 4.4 明确不做

| 编号      | 不做的事                          | 理由                                                                                                                                                                            |
| --------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **TR-8**  | **不实现崩溃恢复日志（journal）** | 若进程在 S1 与 S3 之间被强制终止，会留下"两份共存"状态。覆盖此场景需引入 journal + 启动时恢复流程，属明显的增量复杂度；而最坏结果仅为冗余，不影响使用。**此取舍已获用户确认。** |
| **TR-9**  | 不做自动回滚的无限重试            | 补偿只尝试一次，失败即报告                                                                                                                                                      |
| **TR-10** | 不做并行安装 / 断点续传           | 无此需求                                                                                                                                                                        |

## 6. 非功能需求

### 6.1 性能

| 编号       | 需求                                                                                                                                                      |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **NFR-1**  | 所有网络访问、PM 命令执行、子进程管理**必须在后台线程**执行。UI 线程不得出现可感知的阻塞。（依据：npm registry 实测 4.1 s，`npm install` 可达 30 s 以上） |
| **NFR-2**  | 程序启动后主窗口须在 1 秒内可交互，网络相关区域以加载态呈现。                                                                                             |
| **NFR-3**  | 网络请求超时必须设置上限（建议 15 s），超时后进入失败路径而非无限等待。                                                                                   |
| **NFR-4**  | 托盘常驻期间空闲 CPU 占用应接近零。                                                                                                                       |
| **NFR-11** | **日志缓冲上限 2000 行**，超出时丢弃最旧行。                                                                                                              |
| **NFR-12** | FR-34 的"每个插件查最新版"**必须并行、必须在后台线程**：N 个包不得串行等待。（依据：本机单次 registry 请求实测 4.1 s，6 个串行 ≈ 25 s —— 那会让插件卡在半分钟里停在"检查中…"） |

**NFR-11 的依据**：`dsh web` 的输出在理论上无界，而 §8.2 的多条验证（V-12、V-14 等）会长时间运行。日志模型若无上限将持续占用内存。超出上限时丢弃最旧行，而非拒绝新行 —— 排查问题时最新的输出远比最旧的输出有价值。

**NFR-12 的落地**：`plugin::fill_latest` 用 `std::thread::scope` 每包一线程（`docs/superpowers/specs/2026-09-22-plugin-manager-design.md` §4.3）。单包失败（超时 / 404 / 版本号非法）只让那一行显示"—"，不牵连其他行 —— 与 FR-6 的"单个 PM 探测失败不影响其他"同款。

### 6.1.1 NFR-2 的实测预算

启动延迟已用最小 spike 实测（详见 [ARCHITECTURE.md](ARCHITECTURE.md) §2.4.3）：

| 时点                                    | 实测        |
| --------------------------------------- | ----------- |
| `MainWindow::new()` 返回                | **10.5 ms** |
| `show()` 返回（窗口已就绪）             | **12.5 ms** |
| 首次 UI 排空定时器回调（事件循环已启动） | **290.8 ms** |

**结论**：NFR-2 的 1 秒预算**留有极大余量**。窗口在约 12.5 ms 即可交互，**约 80 倍优于要求**。

**但需注意一个实现后果**：事件循环启动存在约 **278 ms 的固定延迟**（Slint/winit 初始化后端与窗口系统的开销）。因此程序启动后到"第一次收到后台数据"之间存在约 290 ms 的空窗期，此期间界面必须以加载态呈现（NFR-2 后半句），**不得**显示"未检测到"之类的误导性结论。

### 7.1 Windows 平台强制事项

| 事项           | 要求                                | 违反后果                               |

| 二进制子系统   | `#![windows_subsystem = "windows"]` | GUI 后出现黑窗口                       |

### 7.2 Slint 强制事项

| 事项                | 要求                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 事件循环            | 必须用 `run_event_loop_until_quit()`，否则窗口隐藏即退出                                                                 |
| 窗口关闭拦截        | `slint::Window::on_close_requested(..) -> CloseRequestResponse`，返回 **`HideWindow`**。**不是** `close-requested` 回调 + `hide()`（该回调在 Slint 语言中不存在，见 FR-23） |
| 状态同步            | Rust 侧单一状态源，推送到窗口与托盘两个实例（FR-25）                                                                     |
| 托盘组件            | 顶层组件 `inherits SystemTrayIcon`，恰好一个 `Menu` 子元素                                                               |
| 托盘图标            | `icon` 为空时图标不会被创建，必须提供非空图片资源                                                                        |
| **std-widgets 导入** | `ListView` / `ComboBox` / `Button` / `ScrollView` / `AboutSlint` 等**不是语言内建元素**，必须显式 `import { .. } from "std-widgets.slint";` |
| markdown            | 用 `StyledText::from_markdown`，不引入额外库；渲染前必须预处理标题与 HTML（FR-27）                                        |
| 字体                | 依赖系统字体自动获取，不嵌入字体（CON-9）                                                                                |
| feature             | 使用默认集，不裁剪（CON-2）                                                                                              |

**⚠️ 一条必须靠人工评审守住的纪律**

`slint::Timer` 被标注为 `!Send`，但实测证明其回调签名**并不强制 `Send`**（[ARCHITECTURE.md](ARCHITECTURE.md) §2.4.1）。也就是说，Slint 是用**约定**而非类型系统保证线程安全 —— **类型系统不会拦住"把 `Rc` 挪到别的线程"这个错误**。

因此代码评审时必须人工确认：**`Timer` 及其回调捕获的所有 `Rc` 永不离开 UI 线程**。

### 8.5 动工前已完成的验证

以下两项原属实现风险，已在编写本文档 v1.1 前用最小 spike 实测关闭，**不留待实现阶段**（详见 [ARCHITECTURE.md](ARCHITECTURE.md) §2.4）：

| 项                             | 结论                                                                                                                            |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `Timer` 回调的 `Send` 约束     | ✅ **无 `Send` 约束**。闭包可捕获 `Rc<RefCell<..>>` / `Rc<VecModel<..>>` / `mpsc::Receiver<..>`。定时器排空方案（架构决策 3）成立 |
| `close-requested` 的拦截语义   | ✅ API 为 `slint::Window::on_close_requested(..) -> CloseRequestResponse`；`HideWindow` = 接受关闭并隐藏，`KeepWindowShown` = 取消关闭 |
| Timer 精度                     | ✅ 实测平均 50.5 ms / 抖动 ±1.2 ms（目标 50 ms）。**未被节流**，80 ms 排空间隔可靠                                                |
| 启动延迟                       | ✅ 窗口 12.5 ms 就绪；事件循环启动延迟约 278 ms（见 §6.1.1）                                                                     |

**意义**：这四项都不是"实现时再看"的问题 —— 它们的结论直接决定架构形态。提前关闭避免了基于错误假设的返工。
